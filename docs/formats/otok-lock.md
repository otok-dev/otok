# `otok.lock` — resolved inputs, format 1

Status: draft. Common rules are in [README.md](README.md); the manifest in [otok-toml.md](otok-toml.md).

`otok.lock` is written by otok next to `otok.toml` and committed to the project. It records **what to
fetch**: for every library the exact recipe, version, revision and the hashes of every input. With it,
teammates and CI build from exactly the same inputs (DESIGN 5.3).

It does not record options, platforms, deployment versions or the configuration. Those are computed
from `otok.toml` (and the selected profile) together with the locked recipes, deterministically, every
time. This is what lets one lock serve every profile (`otok-toml.md` 8).

It holds the graphs of the systems the project is built on, `systems` (`docs/PLAN.md` decision 88): of each target and
environment of the project (`otok-toml.md` 4.9) whose system is one of them or any (`*/ndk`), and the tool graphs of those
systems (one per environment of a system its tools are built in, `otok-toml.md` 7). `build-on` says where the project may
be built; the lock, where it is. A machine of a system the lock does not name adds it: `otok install` there resolves its
graphs too, keeping the locked versions where they qualify, and the lock is committed with them. Which graphs a lock holds
depends on the lock and the project, never on the machine resolving them (decision 82).

## 1. Example

A project with `[windows] build-on = ["windows/msvc", "linux/clang-cl"]`, whose boost has a variant for each:

```toml
# Generated by otok. Do not edit.
format = 1
systems = ["linux", "windows"]

[[package]]
library = "boost"
target = "windows"
build-on = ["linux/clang-cl"]
recipe = "apotocki/boost"
variant = "windows-clang-cl"
version = "1.92.0"
revision = 3
recipe-source = { git = "https://github.com/otok-dev/recipes", commit = "1ad90a68…", path = "recipes/boost/1.92/windows-clang-cl" }
recipe-sha256 = "…"
source = { url = "https://archives.boost.io/release/1.92.0/source/boost_1_92_0.tar.bz2", sha256 = "…" }
license = "BSL-1.0"
dependencies = ["zlib"]
tool-dependencies = ["cmake@4.4.5", "ninja@1.13.2"]

[[package]]
library = "boost"
target = "windows"
build-on = ["windows/msvc"]
recipe = "apotocki/boost"
variant = "windows-msvc"
version = "1.92.0"
revision = 1
recipe-source = { git = "https://github.com/otok-dev/recipes", commit = "1ad90a68…", path = "recipes/boost/1.92/windows-msvc" }
recipe-sha256 = "…"
source = { url = "https://archives.boost.io/release/1.92.0/source/boost_1_92_0.tar.bz2", sha256 = "…" }
license = "BSL-1.0"
dependencies = ["zlib"]

[[package]]
library = "zlib"
target = "windows"
build-on = ["linux/clang-cl", "windows/msvc"]
recipe = "apotocki/zlib"
variant = "windows"
version = "1.3.2"
revision = 1
recipe-source = { git = "https://github.com/otok-dev/recipes", commit = "1ad90a68…", path = "recipes/zlib/1.3/windows" }
recipe-sha256 = "…"
source = { url = "https://zlib.net/zlib-1.3.2.tar.gz", sha256 = "…" }
license = "Zlib"

[[tool-package]]
library = "cmake"
build-on = ["linux/gcc"]
recipe = "apotocki/cmake"
variant = "linux"
version = "4.4.5"
revision = 1
recipe-source = { git = "https://github.com/otok-dev/recipes", commit = "1ad90a68…", path = "recipes/cmake/4.4/linux" }

```

## 2. Structure

| Key | Type | Meaning |
|---|---|---|
| `format` | integer | Lock format version; `1`. A lock of another format is a newer otok's: every command reading it fails, saying that it needs a newer otok, and none writes over it (common 1.4). (Drafts before the first release had higher numbers, `docs/PLAN.md` decision 88; such a lock is deleted by hand.) |
| `systems` | array of `windows`, `linux`, `macos`, sorted | The systems of the machines the project is built on, whose graphs the lock holds (`docs/PLAN.md` decision 88); omitted when empty. `otok install` adds the system of its machine when the project is built on it (an environment of that system or `*`); `otok update --drop <system>` removes one. Without a lock, on a machine the project is not built on, every system is resolved, for `tree`, `audit` and the like. |
| `package` | array of tables | Libraries built for the target slices (`[deps.*]` and their dependencies), each for the graphs of its `target` and `build-on`. |
| `tool-package` | array of tables | Libraries built for the tool slice (DESIGN 6.8), each for the tool graphs of its `build-on` (`otok-toml.md` 7). Resolved separately: a library may appear in both arrays with different recipes and versions, and in this one with several versions (5.7). |

A **graph** is a target and an environment of a target table of the project (`otok-toml.md` 4.9), or for tools an
environment of `[otok] tool-build-on` (`otok-toml.md` 3). An entry is in the graphs its `target` and `build-on`
name. The entries of one graph are what it builds: two `package` entries of a library never share a graph, nor two
`tool-package` entries of a library and version. Entries equal in every key but `build-on` are written as one, with the
environments of both.

A **tool reference** is `<library>@<version>`: the `tool-package` entry of that library and version in the tool graph
where it is built (`ninja@1.13.2`).

Each package:

| Key | Type | Meaning |
|---|---|---|
| `library` | library name | Unique within a graph. |
| `target` | target name (common 4) | `package` only: the target of the graphs. |
| `build-on` | array of environments (common 4.2) | The environments of the graphs, as the project's `build-on` or `tool-build-on` writes them (`*/ndk` stays one). |
| `recipe` | recipe id, or `"git"`, or `"path"` | How the recipe was chosen (`otok-toml.md` 6.1). |
| `variant` | recipe name syntax | The recipe's `variant` (`recipe-toml.md` 3), as the index holds it; omitted for git and path recipes. |
| `index` | index name | The index of the project the recipe was taken from (`otok-toml.md` 6.4); omitted for `default` and for git and path recipes. |
| `version`, `revision` | version, integer | Chosen upstream version and the variant's recipe revision. The version is the same in every graph of the library (5.4). |
| `recipe-source` | `{ git, commit, tag?, path }` or `{ path }` | Where the recipe tree was taken from: the repository and commit (with its tag, when one is named) of the index entry or of a git recipe, or a path inside the project (3). |
| `recipe-sha256` | hex | Hash of the recipe tree (`recipe-hash.md`). |
| `source` | `{ url, sha256, mirrors? }`, `{ git, commit, tag?, submodules? }`, `{ path, sha256 }` or `"local"` | The library's source as fetched (3). A `tag` is recorded when the recipe names one (`recipe-toml.md` 4): it lets a locked project fetch from any server. `mirrors`, recorded when the recipe lists them, are where the archive may also be downloaded from (`cache.md` 3.1). |
| `resources` | array of `{ name, url, sha256, mirrors? }` or `{ name, git, commit, tag? }` | The recipe's `[[resource]]` entries; omitted when empty. |
| `license` | SPDX expression | From the recipe; lets `otok audit` check `[policy]` without fetching anything. |
| `dependencies` | array of library names, tool references in `tool-package` | Every library this package may depend on in some profile (5), found in the same graphs; omitted when empty. Tool dependencies of a target package are listed in `tool-dependencies`. |
| `tool-dependencies` | array of tool references | The tool packages this package's build uses (its toolchains and `[tool-deps]`, `recipe-toml.md` 10, 13), found in the tool graphs of the system it is built on. |

Recording the recipe's repository and commit (not only its id) means a locked project can fetch
everything without consulting the index, and that a changed index cannot change what a locked project
builds: `recipe-sha256` and the source hash must still match.

## 3. Local inputs

Paths are written to the lock only when they stay inside the project, which is committed with the
lock (common 6):

| Manifest | Lock |
|---|---|
| `recipe = { path = "recipes/foo" }` inside the project | `recipe = "path"`, `recipe-source = { path = "recipes/foo" }`, with `recipe-sha256` |
| `recipe = { path = "../otok-recipes/foo" }` outside | `recipe = "path"`, `recipe-source = "local"`, no hash |
| `source = { path = "vendor/foo" }` inside | `source = { path = "vendor/foo", sha256 = … }` (tree hash, `recipe-hash.md`) |
| `source = { path = "../foo" }` outside | `source = "local"` |

`"local"` entries are not reproducible: `otok install --locked` fails while any is present
(`otok-toml.md` 6.3), and `otok install` warns.

## 4. Writing rules

- Packages are sorted by `library`, then `target` (tool packages: `version`, as text), then the first environment of `build-on` (environments in
  `build-on` sorted as text); keys appear in the order of section 2; inline tables keep their
  key order; `\n` line endings. The same resolution always produces the same bytes, so diffs show
  only real changes.
- The file is rewritten only when its content changes.
- A hash mismatch between the lock and a fetched input is an error, never a reason to rewrite the
  lock: a moved tag or a replaced archive must not pass silently (DESIGN 11, item 1). In every
  command (`install`, `update`, `fetch`, …) this means:
  - a recipe taken from git at the locked commit and path whose tree hash differs from
    `recipe-sha256` is an error;
  - a package whose recipe tree is unchanged (same `recipe-source` and `recipe-sha256`) must keep
    its `version`, `revision`, `source` and `resources`; a difference means the lock was edited, and
    is an error. Source overrides (`source = { path }` or `"local"`) are exempt: they come from the
    manifest;
  - an archive whose download does not match its `sha256` is an error;
  - recipes and sources by path inside the project change with the project: a new hash is written.

  To accept new contents deliberately, remove the package from `otok.lock` and run `otok install`.

## 5. Resolution

This section defines the result of resolution; the algorithm may differ as long as the result is the
same.

### 5.1 Inputs

The manifest with its fragments (its target tables' `build-on` and `[otok] tool-build-on` give the graphs), every
profile of the manifest, the index (or the git/path recipes), the advisories, and the current lock (as a preference, and its
`systems`, 2). Of the machine resolving, its system only, which it adds to `systems` (`docs/PLAN.md` decision 88): the graphs
of the other systems of the lock are resolved like its own, whether the machine has their environments or not.

### 5.2 One graph for all profiles

Profiles cannot change recipes, versions or the set of direct dependencies (`otok-toml.md` 8), but
through options and platforms they can activate conditional dependencies (`recipe-toml.md` 9.1). The
lock therefore covers the union: a dependency edge is part of the locked graph if its `when` holds in
the base configuration or in any profile, for any slice that profile builds. Each library gets one
version for all profiles.

The same holds across graphs (2): each graph is resolved for every profile, and the profiles never add graphs, which
come from `build-on` (`otok-toml.md` 8).

### 5.3 Choosing recipes

For each library, the recipe is the one chosen by the project (`[deps.<library>]` or
`[tool-deps.<library>]`). Otherwise it is the `default-recipe` of its dependents; if dependents name
different default recipes, resolution fails and asks the project to choose one. This holds for the tool packages too,
whose versions may differ (5.7): every tool package of a library has one recipe. A tool a recipe takes from a
dependency (`[deps.<library>] toolchains`, `recipe-toml.md` 9) has that dependency's recipe; a project choosing another
in `[tool-deps.<library>]` fails resolution.

In each graph, the recipe id gives the variant whose `build-on` covers the graph's environment and whose `supported`
holds the platforms the graph builds (`recipe-toml.md` 6.1), else the variant of the first environment substituting
for it (common 4.2, `otok-toml.md` 4.9), in which the package is then built: a `default-recipe` names the id, never a
variant, so a recipe's dependencies follow it into every graph. A git or path recipe is its own variant and must cover
every graph it is in, or an environment substituting for it. The entry's `build-on` names the graphs; the environment
it is built in follows from its variant, so the lock does not repeat it.

### 5.4 Choosing versions

For each library of the target graphs (tools: 5.7), the chosen version satisfies every constraint on it (project and
dependents, in any profile and any graph), honors the pre-release rules (common 3.2), is not withdrawn by an advisory, and has a variant
for every graph the library is in: **one version in every graph** (`docs/PLAN.md` decision 82). Among
those, the locked version and revision are kept when they still qualify; otherwise the highest
version is chosen, with, per variant, its highest revision that is not withdrawn. A version left out because a graph
has no variant of it is named when resolution fails, with the graph (`1.93.0 (r1): for 'windows' in linux/clang-cl: no
variant of apotocki/boost`). A newly published revision therefore does not make a lock stale; `otok update` moves to
it. When no assignment satisfies all constraints, resolution fails and names the constraints and who imposes them.

### 5.5 Options

For each configuration (base and each profile), options and active edges are the smallest fixed
point of:

- the project's option values are requests;
- an edge (a dependency) is active when its package is in the graph and its `when` holds, per slice,
  with the merged values of that package (`recipe-toml.md` 8.1);
- the `requires-options` of every active edge are requests to its dependency, and so is its `linkage`, per
  platform: the dependency's linkage when the project chooses none (`otok-toml.md` 5).

Requests are only ever added, never withdrawn, so the fixed point exists and is reached in any order.
**Requests may switch edges on, never off:** an edge whose `when` holds with the package's initial
values (the project's values, otherwise the defaults) must still hold with the merged values. When a
request through the graph would switch an edge off, resolution fails and names the option, the edge
and the requesters. This keeps the result independent of the order in which requests arrive: whether
the edge was ever "seen" active never matters. Exclusive options that receive different values fail as
`recipe-toml.md` 8.1 says.

The computed options and linkages are not stored in the lock; they are recomputed on every run and enter the build
cache key (`cache-key.md`). `otok tree` and `otok why` show them (DESIGN 5.4).

### 5.7 Tools

A tool is a detail of the build that uses it (`docs/PLAN.md` decision 87): every tool dependency of a package (its
toolchains and `[tool-deps]`, `recipe-toml.md` 10, 13) is resolved for that edge alone, as a graph of its own rooted at
the edge, holding the tool and what it links (`dependencies`, unified there as in a target graph, one version each) in the
tool graphs of the system (`otok-toml.md` 7). The tool dependencies of the packages of that graph are edges of their own
again. So two packages needing incompatible versions of one tool each get theirs, and nothing of one tool's graph
constrains another's.

- In each such graph a library gets the highest version its constraints allow, the version the package's lock entry
  references (its `tool-dependencies`, then their `dependencies`) when it still qualifies, the project's
  `[tool-deps.<library>]` constraint if any.
- A tool taken from a dependency (`[deps.<library>] toolchains`) has exactly the version of that dependency in the
  package's graph.
- The tool package of a library and version is the same in every graph it appears in: one entry, one build. Two edges
  reaching one with different options fail resolution, naming both.
- A tool dependency on a library whose own tool dependencies lead back to it is a cycle and fails resolution.

### 5.6 Checks

After resolution: license policy (`otok-toml.md` 9) for every package in either array, advisories
(DESIGN 7.3), recipe `[apple] xcode` constraints and toolchains (checked before building).

## 6. Staleness and updates

The lock is **stale** when resolving with it as a preference would produce a different lock: a
dependency added or removed, a constraint the locked version no longer satisfies, a recipe choice
changed, a conditional dependency newly activated by an option or a profile, a withdrawn locked
version, a machine whose system the project is built on and `systems` does not name (2).

| Command | Missing or stale lock | Valid lock |
|---|---|---|
| `otok install` | resolves, keeping locked versions where possible, writes the lock | uses it |
| `otok install --locked` | fails, listing what would change | uses it |
| `otok update` | re-resolves without preferences (highest versions within constraints) and writes the lock | same |
| `otok update <library>` | re-resolves `<library>` without preference, keeping every other locked version where possible | same |
| `otok update --drop <system>` | as `otok update`, without the graphs of that system, which the lock no longer names (not this machine's) | same |

A version withdrawn by an advisory makes the lock stale, but `install` does not silently replace it:
it stops with the advisory, unless `--allow-advisory=<id>` is given (DESIGN 7.3), and `otok update`
moves to another version.
